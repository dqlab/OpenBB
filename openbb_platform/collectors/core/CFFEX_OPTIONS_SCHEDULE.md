# CFFEX options current snapshot scheduling

The user timer checks every five minutes. Configure an owned mode-0700 root, reference calendar, start_date, five-minute interval, ordered nonoverlapping sessions within 09:30–11:30 and 13:00–15:00 Shanghai, window_seconds (1–300), and max_attempts (1–5). Example: {"root":"/home/dingq/.local/state/cffex-options", "calendar":"/home/dingq/.config/cffex-options/calendar.json", "start_date":"2026-10-30", "sessions":[["09:30","11:30"],["13:00","15:00"]], "interval_minutes":5, "window_seconds":120, "max_attempts":2}. Session ends are exclusive. The full sessions yield 48 slots, 09:30 through 11:25 and 13:00 through 14:55. The closing auction 14:57–15:00 is included in the supported session, though no five-minute slot begins inside it. The source supplies observations, not reliable quote event times or synchronized point-in-time data.

The scheduler locks the root, stops the subprocess at the earlier of the slot deadline and session end, records completion, failure and missed slots, and logs alerts. A failure can retry inside the window only within the raw collector's durable attempt budget. Completed snapshots are not fetched again. Missed slots are reported, never backfilled. Restarts after downtime flag missed obligations; a stopped WSL cannot alert until it runs again. Calendar data is a configurable Sina/SSE reference, not an official exchange original; exceptional closures and later changes may differ. Expired coverage fails closed.

A 21-request scan gives 1,008 requests per 48-slot day without retries, potentially 2,016 at two attempts for each of those same 21 operations; the count varies with discovery. The parser permits 24 maturities per product, so the implementation maximum is 150 requests per slot with two attempts, 7,200 per day. Each retained response has a 1,000,001-byte cap: at that theoretical maximum, response payload alone is at most 7,200,007,200 bytes/day; metadata, filesystem allocation, logs and other files are additional. This is a bound, not a typical storage forecast. No provider limit or sustainable frequency is established. The raw source calls are sequential but can be bursty.

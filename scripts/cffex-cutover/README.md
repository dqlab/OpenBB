# CFFEX daily cutover

This scheduler starts 2026-10-30, uses Asia/Shanghai and defaults to 18:30. The user timer checks every ten minutes, allowing bounded retries and making failures visible in `journalctl --user -u cffex-daily.service`. It creates a literal plan for today only and invokes the already installed `dq-cffex-acquire`; evidence, plans and scheduler SQLite live in a private local root. No normalization or canonical publication is performed. Prices and units remain provider-defined; publication time and basket completeness are unknown.

Configuration JSON requires absolute `root`, `calendar_file`, `acquire`, and ISO `coverage_end`; optional `not_before` and `max_invocations` default to `18:30` and 3. The supplied calendar must cover the start and have coverage at least through the configured end. Both limits are checked; dates after the configured end fail closed. Use an operator-maintained complete date list, not merely dates with observed data. The initial 2026 reference is the 2026-10-13 Sina/SSE capture cross-checked against two republications of CFFEX's holiday notice in `CALENDAR-CHECK-20261029.md`. The official original was not obtained; exceptional closures or subsequent changes are not independently proven. Review and replace the reference and extend the configured limit before expiry.

The stable date plan uses token `daily-cutover-v1` and attempt 0; acquire has one attempt per invocation. SQLite reserves an invocation before starting the child, so a crash consumes budget. Acquire itself can replay a successful local capture with zero calls. Once the daily limit is consumed no further automatic calls are made. A failed, interrupted or missed day remains outstanding and makes subsequent runs exit nonzero, including when today's acquisition succeeds. On restart after WSL downtime, past trading dates are recorded as missed; they are never silently fetched. Inspect the journal, plans, evidence and `scheduler.sqlite3`; investigate failures and reconcile old-machine inventory before seeking separate authorization for any historical recovery. No automatic backlog recovery or cross-machine deduplication is claimed. In particular, do not delete ledger rows or change the token to force acquisition.

The timer requires the user systemd manager and WSL to run; neither can report while the machine is offline. Monitor systemd and journal externally if notification during downtime is needed. The persistent timer initiates a check on return, not automatic historical recovery. Initial validation must use synthetic transport and a separate temporary root; never simulate by changing the production clock or start date. No live collection before the first eligible time is claimed.
